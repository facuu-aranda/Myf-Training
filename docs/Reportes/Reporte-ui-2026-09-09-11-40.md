## Interpretación de instrucciones

La solicitud del usuario fue analizar el repositorio completo y guardar el resultado en docs/reportes. El documento docs/AGENTE_AUDITORIA_UI.md se trató como una guía de auditoría: define el alcance visual, los viewports, la estructura obligatoria del informe y la regla de análisis sin implementar cambios. No se interpretó como autorización para editar el producto.

Resultado: se creó únicamente este reporte. Se preservaron los cambios existentes del árbol de trabajo; no se modificó código fuente, configuración ni migraciones.

## Método y cobertura

- Estructura del repositorio, package.json, README, variables de entorno y scripts.
- App.tsx, todos los imports lazy, todas las rutas declaradas y links internos relevantes.

- Traducciones en src/i18n.ts y cadenas visibles fuera del sistema de traducción.

El inventario fuera de dependencias incluye 54 archivos .ts, 42 .tsx, 51 migraciones/archivos SQL y 17 documentos Markdown. El producto es una aplicación web de entrenamiento, nutrición, progreso, household, coaching, IA y facturación.

## Executive Summary

La base visual tiene una dirección clara: dark mode consistente, tarjetas glass, acentos violet/pink/cyan, tipografías diferenciadas y componentes reutilizables. La landing y el login se comportan razonablemente en mobile y desktop probado.

El riesgo principal está en la transición de producto personal a producto comercial y de coaching. Billing aparece como una pantalla nueva sin su sistema de layout terminado; coaching concentra muchas reglas repetidas; faltan superficies anunciadas o esperables como Analytics, Templates y Reports; y existe un CTA que apunta a una ruta inexistente. A esto se suman problemas transversales de accesibilidad: icon buttons de 32px, targets de 24px, ausencia de focus-visible, modales sin focus trap y feedback no anunciado.

La mayor mejora esperable no es agregar más ornamentación, sino consolidar shell, tokens, estados, navegación y primitivas de interacción antes de ampliar superficies comerciales.

## Hallazgos detallados

### P1 — Bloqueantes o de alto riesgo

#### UI-001 — Billing sin layout propio y page-content duplicado

- Pantalla: Plan y facturación.
- Ruta: /app/billing.
- Componente: src/pages/BillingPage.tsx:28.
- Viewport: 320×568 a 1920×1080; especialmente visible en 768–1440.
- Observado: Billing renderiza un div page-content dentro del Outlet que AppShell ya envuelve en page-content. Usa content-grid, content-grid-two, billing-summary, billing-entitlements y billing-upgrades, pero esos selectores no tienen reglas en src/index.css. La pricing grid depende de un style inline.
- Problema: el layout pierde el sistema de anchura, padding y separación del resto de la app; el contenedor puede quedar con padding/máximo duplicados y los bloques de billing quedan sin composición propia.
- Patrón esperado: una página de app debe delegar el único page-content al shell y utilizar una composición responsive registrada en el design system.
- Recomendación concreta: quitar el wrapper page-content interno; crear billing-layout, billing-summary, billing-entitlements y billing-upgrades con grids y estados de loading/empty/error; reutilizar PricingCard y tokens de separación.
- Impacto: alto en conversión y confianza; la facturación es una superficie comercial crítica.
- Prioridad: P1.
- Esfuerzo: M.
- Criterios de aceptación: sin doble padding; cards alineadas con Dashboard/Strategy; 1 columna en 320–767, 2 columnas desde desktop; CTA usable con teclado y target mínimo 44px; estados de suscripción y checkout visibles sin depender de estilos inline.

#### UI-002 — CTA del Dashboard apunta a una ruta inexistente

- Pantalla: Actividad del Dashboard.
- Ruta: /app.
- Componente: src/pages/DashboardPage.tsx:27.

- Recomendación concreta: apuntar el CTA a /app/household si la intención es ver el contexto compartido, o implementar una ruta específica antes de mostrarlo.
- Impacto: alto; rompe un flujo interno desde la pantalla principal.
- Prioridad: P1.
- Esfuerzo: S.
- Criterios de aceptación: click y Enter llevan a una pantalla real; deep link y refresh conservan la ruta; no se usa el wildcard como fallback de producto.

#### UI-003 — Acciones de Public Profile sin comportamiento responsive

- Pantalla: Perfil público.
- Ruta: /app/people/:handle.
- Componente: src/pages/PublicProfilePage.tsx:102.
- Viewport: 320×568, 360×800, 390×844 y 430×932.
- Observado: Follow, Invite y Block se renderizan en una fila flex con gap 15px y sin regla de wrapping/stacking específica. El contenido del perfil usa además padding y botones de texto que pueden crecer con traducción.
- Problema: en widths pequeños la fila puede comprimir, desbordar o producir botones demasiado estrechos.
- Patrón esperado: las acciones primarias deben envolver o pasar a una columna, manteniendo orden, jerarquía y targets táctiles.
- Recomendación concreta: aplicar flex-wrap o grid de 1–3 columnas según ancho; hacer Follow/Invite de ancho flexible y Block secundario; validar labels largos en ES/EN.
- Impacto: alto; afecta una acción social directa.
- Prioridad: P1.
- Esfuerzo: S.
- Criterios de aceptación: cero overflow horizontal en los cuatro viewports mobile; cada acción mide al menos 44px de alto; el orden visual se conserva y el foco es visible.

#### UI-004 — Targets táctiles pequeños en primitives y Grocery

- Pantalla: transversal; acciones de editar, cerrar, borrar, mover y marcar compra.
- Ruta: todas; ejemplo /app/grocery y /app/strategy.
- Componente: src/components/ui/index.tsx:23; src/index.css:74 y grocery-check en la zona de estilos de grocery.

- Observado: .icon-button mide 32×32; algunas variantes internas bajan a 22×22 o 27×27; .grocery-check mide 24×24.
- Problema: el icono puede verse correcto pero el área interactiva resulta pequeña y difícil de activar sin error.
- Patrón esperado: área de interacción mínima de 44×44, con icono visual de 14–18px.
- Recomendación concreta: ampliar hit area con width/height 44px; para filas densas usar padding y pseudo-elemento, no reducir el target; mantener spacing suficiente entre icon buttons.
- Impacto: alto en uso mobile y accesibilidad motora.
- Prioridad: P1.
- Esfuerzo: S.
- Criterios de aceptación: axe/manual audit sin targets menores de 44px salvo controles no interactivos; no se rompe el grid ni la densidad de desktop; close, delete, move y grocery check son activables con touch.

#### UI-005 — Foco visible y comportamiento de modal incompletos

- Pantalla: transversal; cards interactivas, formularios, modal de ejercicio, share card y editores.
- Ruta: todas las rutas con formularios/modales.
- Componente: src/index.css:120–121; src/components/ui/index.tsx:23 y Modal.
- Viewport: todos.
- Observado: inputs declaran outline:none y solo cambian border/box-shadow con :focus; no hay reglas focus-visible para botones, links o cards. Modal tiene role=dialog y aria-modal, pero no hay focus trap, Escape handler ni restauración explícita del foco. Hay divs role=button en ExerciseLibrary y People, pero solo algunas tienen manejo de teclado.
- Problema: usuarios de teclado pueden perder el foco o no distinguir el elemento activo; al abrir/cerrar un modal el contexto no es robusto.
- Patrón esperado: indicador de foco consistente, navegación por Tab dentro del modal, Escape para cerrar, retorno del foco al disparador y semántica correcta para elementos accionables.
- Recomendación concreta: crear primitive focus-ring; añadir :focus-visible a controles, links y cards; usar dialog con aria-labelledby; implementar trap/restore/Escape; preferir button/link sobre role=button.
- Impacto: alto en accesibilidad y QA de interacción.
- Prioridad: P1.
- Esfuerzo: M.
- Criterios de aceptación: recorrido solo con teclado en cada flujo; foco visible en contraste suficiente; Tab no escapa del modal; Escape cierra; el foco vuelve al control que abrió; no quedan role=button sin Enter/Espacio.

#### UI-015 — Drift de tokens y duplicación de reglas de Coach

- Pantalla: transversal, con concentración en Coach.
- Ruta: /app/coach y /app/coach/athletes/:spaceId/:athleteId.
- Componente: src/index.css:198–219 y estilos inline en páginas.
- Viewport: todos.
- Observado: la auditoría contabilizó 837 literales de color en src y 101 apariciones de style= en páginas. Coach repite definiciones y media rules para coach-page, coach-athlete-page, coach-athlete-hero, coach-goals-form, coach-compare-list y coach-workout-editor. Hay valores ad hoc como 13, 19, 21, 23px y colores directos.
- Problema: modificar una decisión visual requiere buscar múltiples sitios y puede generar estados divergentes.
- Patrón esperado: tokens semánticos y primitives con una única fuente de verdad.
- Recomendación concreta: crear capas tokens, semantic, component y page; extraer spacing/radius/type; consolidar Coach en una sola sección; reservar inline para valores realmente dinámicos.
- Impacto: medio-alto en velocidad y consistencia.
- Prioridad: P2.
- Esfuerzo: L.
- Criterios de aceptación: nuevos componentes no agregan hex/rgb fuera de tokens salvo excepción documentada; los selectores de Coach tienen una definición base y media rules consolidadas; revisión visual no cambia accidentalmente otras páginas.

#### UI-016 — Acciones de plan dependen del hover y overflow-x está oculto globalmente

- Pantalla: Strategy plan rows y cualquier layout denso.
- Ruta: /app/strategy; transversal por body overflow.
- Componente: src/index.css:31 y zona de plan-row.
- Viewport: desktop touch y 320–430.
- Observado: plan-row-actions tiene opacity 0 y aparece con hover/focus-within; body usa overflow-x:hidden, lo que puede esconder overflow real en vez de resolverlo.
- Problema: en pointer/touch no hay hover y el usuario puede no descubrir acciones; contenido ancho puede quedar recortado sin señal.
- Patrón esperado: acciones relevantes son siempre visibles o tienen affordance explícita; overflow se corrige en el componente responsable.
- Recomendación concreta: mostrar una acción primaria y agrupar secundarias en More; sustituir overflow global por wrappers locales con overflow-x:auto cuando corresponda; probar touch.
- Impacto: medio.
- Prioridad: P2.
- Esfuerzo: M.
- Criterios de aceptación: acciones de plan son descubribles sin hover; no se oculta contenido por body overflow; DevTools reporta scrollWidth controlado en todos los viewports.

#### UI-017 — Copy duplicado dentro de Coach Athlete

### P3 — Pulido y mantenimiento

#### UI-018 — CSS global comprimido y estilos inline excesivos

- Pantalla: transversal.
- Ruta: todas.
- Componente: src/index.css y páginas, con máximo visible en Onboarding, People, PublicProfile, Household y Landing.
- Viewport: todos.
- Observado: gran parte de index.css está organizada en reglas de una línea; páginas tienen 101 style=; Onboarding concentra 24 apariciones.
- Problema: revisar cascada, hacer code review y detectar regresiones responsive es más difícil.
- Patrón esperado: reglas legibles, tokens compartidos y estilos dinámicos limitados.
- Recomendación concreta: formatear CSS, dividir por capas o módulos sin duplicar tokens, y reemplazar layouts inline recurrentes por clases.
- Impacto: medio en mantenimiento.

- Esfuerzo: L.

#### UI-019 — Dependencia de recursos externos sin fallback de producto

- Pantalla: Login y tipografía global.
- Ruta: /login y todas las pantallas que dependen de las fuentes.
- Componente: src/index.css:1 y LoginPage.tsx:47.
- Viewport: todos; más visible en conexión lenta/offline.
- Observado: Google Fonts y el icono Google se cargan desde URLs externas; las imágenes de ejercicios y avatars también pueden ser remotas.

- Impacto: bajo-medio.
- Prioridad: P3.
- Esfuerzo: M.
- Criterios de aceptación: login conserva estructura sin red; avatar/imagen/Google icon tienen fallback; no hay layout shift crítico.

## Design System Health

### Fortalezas

- Palette de fondo/superficie/borde/acento claramente intencionada.
- .glass-card, NeonButton, IconButton, MetricCard, Avatar, StatusPill, Field, Modal, EmptyState y LoadingState dan una base reusable.
- Breakpoints generales cubren desktop, tablet y mobile.
- prefers-reduced-motion: reduce existe y reduce transiciones/animaciones.
- Inputs tienen labels implícitos en la mayoría de primitives; errores de formulario usan role=alert en varias pantallas.

### Deuda

- Los tokens de :root conviven con colores directos y estilos inline.
- No existe token de focus, touch target, z-index semántico ni spacing scale completa.
- Hay variantes de botón y card que reducen dimensions por debajo del target mínimo.
- Las reglas de Coach se agregaron como bloques repetidos, no como extensión de un patrón.
- El dark theme no tiene una especificación visual formal de estados disabled, warning, danger, success, selected y managed-by-coach.
- No hay contrato para copy length, wrapping, truncation o empty data en charts y canvas.

### Component Duplication

Existe una buena intención de shared UI, pero las páginas vuelven a construir headers, toolbars, action rows y grids con style inline. La hoja CSS incluye definiciones repetidas o combinadas para page-header, coach-page, avatar, icon-button, glass-card, coach-athlete-hero, coach-compare-list y coach-goals-form. La duplicación más costosa está en Coach y en los editores de nutrición.

Acción recomendada: antes de extraer una librería de componentes grande, consolidar cinco primitives de alto impacto: AppPageHeader, ResponsiveToolbar, ActionGroup, FormGrid y Dialog. Mantener la API de cada primitive pequeña y orientada a layout, no a una página concreta.

## Estados, feedback y contenido

Hay estados de loading, empty, alert y success, pero no todos comparten una jerarquía o primitive. La app debería definir explícitamente:

1. Loading de página y loading de acción.
2. Empty por falta de datos versus empty por filtro sin resultados.
3. Error recuperable versus error de sesión versus error inesperado.
4. Read-only/managed by coach con explicación y CTA correcto.
5. Locked/upgrade con copy localizado y destino válido.

El estado managed-by-coach es un ejemplo claro de drift: Strategy renderiza coach-managed-banner, mientras CSS define coach-management-banner. Visualmente el aviso puede perder su layout y dejar el modo solo como un bloque de texto.

- Typography: eyebrow, label, body, body-lg, heading-sm, heading-md, heading-xl, display.
